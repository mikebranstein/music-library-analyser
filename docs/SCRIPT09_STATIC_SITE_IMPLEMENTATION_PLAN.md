# Script 09 — Static Web Gallery: Design & Implementation Plan

Status: **planning (awaiting approval)**. This document is the design of record for
`scripts/09_static_site.py` and the hand-authored `web/` static site. Nothing here is implemented
yet — per the request, we plan and review (interview) first, then implement on approval.

The master plan (`docs/BAND_COLLECTION_ANALYSIS_PLAN.md`) will gain a §4.10 linking here once
approved.

---

## 1. Purpose

Turn every artifact the pipeline produces (Scripts 01–08) into a **browsable static website** that
mirrors the pipeline's structure: a top-level **dashboard**, one **page per processing phase**, and
**drill-down** all the way from the collection → a piece → a document (PDF) → an individual page,
ending at the **original PDF file** itself. Each phase page explains what that step does and
surfaces its statistics; every summary drills into the details behind it. The site is the
human-facing "front door" to the whole analysis.

It is deliberately split into two clean halves, matching the request:

1. **Hand-authored scaffold** (HTML/CSS/JS): the pages, navigation, layout, charts, and interaction
   logic. Version-controlled, authored by the assistant, and never overwritten by the script.
2. **Script 09 (`09_static_site.py`)**: a deterministic transform that reads the pipeline outputs
   and emits the **data layer** (`web/data/*.js`) and **web thumbnails** (`web/assets/thumbs/…`)
   that the scaffold reads at runtime.

## 3. The `file://` constraint and how we satisfy it (critical)

Decisions #1 and #2 create a hard technical conflict that this design resolves explicitly:

- Browsers **block `fetch()` of local files** from a `file://` page (its origin is `null`), and they
  **block ES modules** (`<script type="module">`) from `file://` for the same-origin reason.
- Therefore the site **cannot** `fetch()` JSON and **cannot** use ES-module `import`.

**Resolution — data-as-JS, classic scripts:**

- Script 09 emits the data layer as **generated `.js` files** (not `.json`) that register onto a
  single global namespace, e.g.:
  ```js
  // web/data/pieces.js  (generated by Script 09)
  window.MLG = window.MLG || {}; MLG.data = MLG.data || {};
  MLG.data.pieces = { /* …curated JSON… */ };
  ```
- Pages load exactly the data files they need with **classic** `<script src="…">` tags (which *do*
  load from `file://`), then a page script renders from `MLG.data`.
- Navigation is **multi-page**: separate `.html` files linked with **relative hrefs** (works from
  `file://`), using `?id=…` query strings that entity pages read via `location.search`.
- Images are `<img src="assets/thumbs/…">` — relative file refs, which load fine from `file://`.
- Dark/light preference persists via `localStorage` (available on `file://`).

> The data is functionally identical to a JSON API; it is only *packaged* as JS so double-click
> works with no server. If we later add a server (the "live" phase), Script 09 can additionally emit
> parallel `.json` for programmatic use with almost no extra work.

We also ship an **optional** convenience: `web/serve.py` (a one-line `http.server` launcher) for
anyone who *prefers* a server, but it is never required.

## 5. `web/` architecture

### 5.1 Folder layout

```text
web/
  index.html                     # Dashboard (landing page)
  pages/
    phase-01-inventory.html
    phase-02-extraction.html
    phase-03-classification.html
    phase-04-expected-parts.html
    phase-05-quality.html
    phase-06-piece-reports.html
    phase-07-collection.html
    phase-08-review-pack.html
    pieces.html                  # piece index (browse/filter all pieces)
    piece.html                   # single piece      (?id=<piece_id>)
    documents.html               # document index
    document.html                # single document   (?id=<doc_id>)
    page.html                    # single page        (?id=<page_id>)
  css/
    theme.css                    # palette + light/dark CSS variables
    layout.css                   # header/nav/grid/breadcrumbs
    components.css               # cards, tables, charts, badges, expanders
  js/
    core.js                      # MLG namespace, formatters, badges, breadcrumb + nav, theme toggle
    charts.js                    # dependency-free inline-SVG charts (bars, donut/gauge, sparkline)
    dashboard.js                 # renders index.html
    phase.js                     # shared phase-page renderer (data-driven from MLG.data.phases)
    entities.js                  # renders pieces/piece/documents/document/page
    router.js                    # tiny query-string / id lookup helpers
  data/                          # GENERATED by Script 09 (do not hand-edit)
    manifest.js                  # run info, totals, per-phase index + stat cards
    dashboard.js                 # curated dashboard KPIs + highlights
    pieces.js                    # full per-piece model (only 5 — kept inline & rich)
    documents.js                 # per-document model (148)
    pages.js                     # per-page model (441)
    phases.js                    # per-phase narrative + stats + distributions + entity tables
  assets/
    thumbs/<piece_id>/<doc_id>__p0001.jpg   # GENERATED downsized web thumbnails
    icons/…                      # small inline/SVG icons (hand-authored)
  serve.py                       # optional local server (not required)
  README.md                      # how to open + how to regenerate (runs Script 09)
```

**Separation of concerns:** everything under `css/`, `js/`, `pages/*.html`, `index.html`,
`assets/icons/`, `serve.py`, `README.md` is **hand-authored** and committed. Everything under
`data/` and `assets/thumbs/` is **generated** by Script 09 and git-ignored (or committed as a
snapshot — open question O3).

### 5.2 The data layer ("site API") emitted by Script 09

Each file assigns curated, web-shaped objects onto `MLG.data.*`. Proposed shapes (abbreviated):

- **`manifest.js`** → `MLG.data.manifest`
  - `site_schema_version`, `generated_at`, `library_root`, `run_ids` (per phase, from record
    envelopes), `totals` `{pieces, documents, pages}`.
  - `phases[]`: `{ id: 1..8, key, title, blurb, script, output_files[], record_count, run_id,
    timestamp, duration: null (deferred), stat_cards:[{label, value, hint}] }`.
- **`dashboard.js`** → `MLG.data.dashboard` — projection of `collection_reports/summary.json` +
  `review_pack/manual_review_queue.json`: headline KPIs, completeness score summary, severity /
  completeness / lookup / quality-band distributions, reason-code frequency, top missing
  sections/instruments, top-priority attention pieces (with links).
- **`pieces.js`** → `MLG.data.pieces[]` — per piece: `piece_id`, `catalog_number`, `title`,
  `folder`, `severity`, `completeness_tier/score`, magnitude counts, `reason_codes`,
  `recommended_actions`, `action_items`, `review_priority` + `priority_breakdown` (from Script 08),
  `expected_parts[]` (with present/missing), `document_ids[]`, `sample_thumbnail`.
- **`documents.js`** → `MLG.data.documents[]` — per document: synthesized `doc_id`
  (`sha256(pdf_path)[:16]`), `piece_id`, `pdf_filename`, `pdf_path`, `pdf_link` (§6.4),
  `predicted_part`, `confidence_tier`, `needs_review`, `is_score`/`score_type`,
  `duplicate_in_piece`, `page_count`, `quality_band`, `ocr_llm_instruments`+`confidence`+`notes`,
  `vision_*`, `thumbnail`, `page_ids[]`.
- **`pages.js`** → `MLG.data.pages[]` — per page: `page_id` (`<doc_id>__p{n}`), `doc_id`,
  `piece_id`, `page_num`, `thumbnail`, render metrics (`render_dpi`, dimensions, `estimated_dpi`,
  `blur_variance`, `skew_angle_deg`, `contrast_std`, `text_density`, `black_white_ratio`,
  `largest_image_coverage`), `orientation`, `staff_line_count`/`has_staves`, `is_blank`,
  `is_image_based`, and collapsible `ocr_text` + `vision_notes`.
- **`phases.js`** → `MLG.data.phases_detail` — per phase, the extra content its page needs beyond
  `manifest` (distribution series for charts, and the drill-down table rows referencing entity ids).

Determinism: stable synthesized ids, sorted keys, fixed float rounding, entities ordered by
`piece_sort_key` / `part_sort_key` / page number.

### 5.3 Thumbnails

- Source: `cache/render/*.png` (referenced by `thumbnail_path` in `pages.jsonl` / piece reports).
- Script 09 downsizes each **referenced** page render to a max dimension (default **480 px**) as
  **JPEG** (or WebP — open question O2) into `web/assets/thumbs/<piece_id>/<doc_id>__p{n}.jpg`.
- Estimated output: ~440 web thumbs × ~30–60 KB ≈ **15–30 MB** (vs 160 MB source).
- Incremental: skip regeneration when the target exists and the source hash is unchanged
  (`--rebuild-thumbs` forces). One representative page-1 thumb per document doubles as the doc/piece
  card image.

## 6. Information architecture & navigation

### 6.1 Global chrome (every page)

- **Header:** site title ("Music Library"), primary nav — **Dashboard · Pipeline ▾ (the 8 phases) ·
  Pieces · Documents** — a **theme toggle** (light/dark), and a **global search box** that queries
  across pieces / documents / pages (client-side, from the loaded `MLG.data`). Index pages
  (`pieces.html`, `documents.html`) additionally have **per-column/table filters** for focused
  browsing (decision O6: both).
- **Breadcrumbs:** e.g. `Dashboard › Pieces › 001 Mexican Hat Dance › …Baritone BC.pdf › p.1`.
- **Footer:** generated timestamp + run id(s) + site schema version.

### 6.2 Dashboard (`index.html`) — the "ultimate" overview

A single screen that both *summarizes* and *launches drill-down*:

1. **Hero KPI strip:** pieces, documents, pages, mean completeness, high-severity count,
   documents needing re-scan — each clickable to the relevant phase/entity view.
2. **Pipeline flow:** the 8 phases as a horizontal strip of clickable cards (icon, phase title,
   one-line blurb, record count, status) — the visual spine that mirrors the scripts.
3. **Collection health:** completeness-tier donut, severity split, quality-band bar, lookup-status
   bar (from `dashboard.js`).
4. **Top priorities:** the review-pack queue (top N) as a ranked, clickable list → piece pages.
5. **Where the gaps are:** top missing sections / instruments, and reason-code frequency.
6. **Recent/notable:** e.g. pieces missing a score, most low-quality documents — each a drill link.

### 6.3 Phase pages (one consistent template ×8)

Every phase page uses the **same** data-driven template (`phase.js` + `MLG.data.phases`):

- **What this step does** — a plain-language narrative (authored, stored in the phase blurb).
- **Run facts** — script filename, output files, `run_id`, timestamp, record count, and a
  **duration** slot (currently "not captured yet"; see §9).
- **Stat cards** — the phase's headline numbers.
- **Charts** — distributions specific to the phase (e.g. Phase 05 quality bands; Phase 03
  confidence tiers; Phase 04 completeness tiers / lookup status).
- **Drill-down table** — the entities this phase produced, each row linking to its entity page.
- **Notes / known limitations** — authored caveats.

Phase-to-content mapping (summary):

| Phase | Page focus | Primary drill target |
|------:|------------|----------------------|
| 01 Inventory | Folders & PDFs discovered, page counts, sizes | Documents |
| 02 Extraction | Text vs OCR vs image-based, OCR recovery, render stats | Pages |
| 03 Classification | Predicted part, confidence tiers, needs-review, duplicates | Documents |
| 04 Expected parts | Expected instrumentation, completeness tier/score, lookup status | Pieces |
| 05 Quality | Quality bands, blur/skew/contrast, handwritten/legibility | Pages / Documents |
| 06 Piece reports | Per-piece synthesis, severity, reason codes | Pieces |
| 07 Collection report | Library-wide aggregates & distributions | Dashboard / Pieces |
| 08 Review pack | Prioritized queue, weights, action items | Pieces |

### 6.4 Entity drill-down (piece → document → page → **PDF**)

- **Pieces index / piece page:** identity + severity + completeness; expected-vs-observed
  instrumentation table (present ✓ / missing ✗); documents list; reason codes + recommended actions
  + action-item targets; review priority + breakdown; sample thumbnail; links onward.
- **Document page:** classification (predicted part, confidence, is-score, duplicate), quality band,
  OCR-LLM instruments/notes (collapsible), vision notation-source/legibility/notes (collapsible),
  page list, the **sample thumbnail**, **and a prominent "Open original PDF" link** (§ below).
- **Page page (deepest):** large thumbnail; the full render/quality metric grid; is-blank/has-staves;
  collapsible **raw OCR text** and **vision notes**; link back up and **link to the original PDF**.

**Original-PDF linking (resolved: O1).** The pipeline stores `pdf_path` *relative to the library
root* (e.g. `001 Mexican Hat Dance/… Baritone BC.pdf`), with the root external to the repo (e.g.
`C:\Temp\NSCB`). The site links to the **real files** via absolute `file://` links, but the base
directory is **not hard-coded into the links** — instead:

- Script 09 emits each document's **relative `pdf_path`** plus a **default `library_root`** (recorded
  in the manifest from `--library-root`).
- The site has a **"Library location" setting** (in the header/settings and persisted in
  `localStorage`). PDF links are composed **client-side** as `file://` + `base` + `pdf_path` at click
  time, so if `web/` (or the library) moves, the user updates one field and every PDF link keeps
  working. The resolved absolute path is also shown as **copyable text** (mitigating browsers that
  restrict `file://`→`file://` navigation).
- Opt-in **`--copy-pdfs`** still bundles originals into `web/assets/pdfs/…` (relative links) for a
  fully self-contained/shareable site. Default off.

## 7. Visual & interaction design

The entire visual layer follows **`docs/WEB_DESIGN_REFERENCE.md`** (the design language of record).
Key bindings from that reference into the site:

- **Palette (CSS custom properties):** the exact light-mode "paper" and dark-mode "stage light"
  token sets — warmed neutrals (no pure black/white), a single **brass accent** (`#9C6B14` light /
  `#D9AE4E` dark) used only once or twice per screen, and semantic `success`/`warning`/`error`
  tokens. The pipeline's own state colors (severity high/review/ok, quality good/review/poor,
  completeness tiers) map onto `error`/`warning`/`success`/muted so state color is consistent — and
  **always paired with a label or icon**, never color alone.
- **Neutrals do ~90% of the work;** accent is the exception. Rough per-screen ratio ~70% surfaces /
  ~20% text+border / ~5% accent / ~5% state.
- **Shape:** 2–4px radius on cards/inputs, 4–6px on buttons, pill shape reserved for small status
  chips only. **Borders (1px hairline), not shadows,** carry structure; overlays (theme menu,
  settings) get one subtle shadow. Tables/dividers are straight-edged (archival catalog feel).
- **Avoid:** gradients, glassmorphism, pure black/white, glowing shadows, skeuomorphism.
- **Light/dark:** a single `data-theme` attribute on `<html>` swaps the variable set; toggle
  persists in `localStorage`; first load respects `prefers-color-scheme`.
- **Components (hand-authored, dependency-free):** stat cards, labelled state badges, sortable +
  filterable tables, breadcrumb trail, collapsible `<details>` for heavy text, and **inline-SVG
  charts** (horizontal bars, a donut/gauge for completeness, distribution bars) styled from the same
  tokens. No charting library — keeps it offline and zero-dependency.
- **Accessibility:** semantic HTML, keyboard-navigable, sufficient contrast in both themes (the
  reference tokens are chosen for this), alt text on thumbnails.
- **Responsive:** CSS grid collapsing to single-column on narrow widths.

## 8. Script 09 (`09_static_site.py`) design

- **Purpose:** deterministic, offline transform of `data/` (+ `cache/render/`) into `web/data/*.js`
  and `web/assets/thumbs/`. It **does not** author or overwrite the scaffold (html/css/js).
- **Inputs:** all pipeline outputs under `--data-dir` (default `data/`); render PNGs under
  `cache/render/`; `--library-root` for PDF links.
- **CLI (proposed):**
  ```text
  09_static_site.py
    --data-dir        data
    --web-dir         web
    --library-root    <path>      (for original-PDF links; recorded in manifest)
    --thumb-max-px    480
    --thumb-format    jpg | webp  (O2)
    --copy-pdfs / --no-copy-pdfs  (default off)
    --thumbnails / --no-thumbnails (skip image step, e.g. for fast data-only rebuilds/tests)
    --rebuild-thumbs              (ignore the skip-if-unchanged cache)
    --mode            full | incremental   (accepted for pipeline uniformity)
    --log-level       INFO
  ```
- **Steps:** load & index all records → synthesize stable ids (`doc_id`, `page_id`) → build the
  curated site-model dicts (pure functions, unit-tested) → render deterministic `.js` files via a
  small `write_data_module(name, obj)` helper (`atomic_write_text`) → generate/skip thumbnails
  (Pillow) → optionally copy PDFs → write `manifest.js` last (records totals + generation time).
- **Reuse `_common`:** `read_jsonl`/`read_json`, `atomic_write_text`, `piece_sort_key`,
  `setup_logging`, the shared vocabulary/order constants.
- **Determinism & schema:** `SITE_SCHEMA_VERSION = "1.0"`; sorted keys; fixed rounding; stable ids.
- **Data-health:** reuse the Script 07/08 pattern — count unreadable/skipped inputs and surface a
  "data health" banner value in the manifest (rendered on the dashboard).

## 9. Deferred: per-phase timing (documented path)

Timing is out of scope for v1 (decision #3). The manifest carries `duration: null` and the phase
pages render "not captured yet." When we choose to add it, the lightweight path is: each of Scripts
01–08 appends `{phase, run_id, duration_s, record_count}` to a shared `data/run_manifest.json` at
the end of `main()` (a ~3-line addition using the `perf_counter` values they already compute), and
Script 09 folds that into `manifest.js`. No UI change is then required beyond removing the
placeholder.

## 10. Testing

- **Unit tests** (`tests/test_static_site.py`, fully offline) for the **pure builders**: id
  synthesis, each `build_*` model function against small synthetic pipeline records, PDF-link
  construction (absolute + copy modes), deterministic serialization, and the data-health accounting.
  The thumbnail/Pillow step is isolated so tests run with `--no-thumbnails` / by calling builders
  directly.
- **Smoke test:** run Script 09 on the real `data/` and assert all expected `web/data/*.js` +
  a sample thumbnail exist and parse.
- **Manual/visual:** open `web/index.html` and spot-check drill-down paths (out of pytest scope).
- Ruff: expect only the established baselines (`N999` numeric module name; `B008` for `typer.Option`
  defaults) — no new codes.

## 11. Implementation phases (on approval)

1. **Scaffold first (authored):** `web/` skeleton — `index.html`, the 8 phase pages, entity pages,
   `css/*`, `js/*` (core, charts, renderers), theme toggle, and a tiny **hand-written sample
   `data/*.js` fixture** so the site renders before Script 09 exists.
2. **Script 09 builders + data emit:** implement the transform to replace the fixture with real
   generated `data/*.js`; wire ids and cross-links.
3. **Thumbnails + PDF links.**
4. **Tests + docs** (README in `web/`, master-plan §4.10, main README section, add Script 09 to the
   pipeline runner).
